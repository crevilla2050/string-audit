Dennis Forge Protocol (DFP) v1

Status: Frozen • Version: 1.0 • Stability: Permanent

Overview

The Dennis Forge Protocol (DFP) defines a deterministic, content-addressed identity layer for transformation plans used by Dennis the Forge.

Identity Model

SHA-256(canonical_plan_json)

Lowercase hex, 64 characters. This hash is the sole identity of a plan.

Canonical URI Format

dfp://v1/forge/<plan_hash>

Example

dfp://v1/forge/1aad05c1a7f1564661c3c18c56773219839ddfd60676929e7b554375f6b8ef34

Validation Rules

  • Prefix must be dfp://
  • Version must be v1
  • Namespace must be forge
  • Hash must be lowercase SHA-256

Namespaces

NamespaceStatus
forgeDefined in v1
plan, diff, branch, metaReserved

Transport Model

DFP defines identity, not transport. Payloads remain valid across files, URLs, QR codes, ASCII text, and printed media.

QR Payload Specification

dfp://v1/forge/<hash>

No JSON. No compression. Pure string protocol.

QR Decoding Modes

ASCII Mode

dennis scan-qr --ascii --from-file <path>
  • Raw payload strings
  • ASCII QR blocks

Image Mode

dennis scan-qr --image --from-file <path>
  • PNG QR codes
  • JPEG QR codes

Cross-Transport Integrity

dennis scan-qr --ascii --from-file plan.txt
dennis scan-qr --image --from-file plan.png

Matching hashes confirm transport integrity.

CLI Guarantees

dennis qr <hash>
dennis qr --ascii <hash>

dennis scan-qr --ascii --from-file file
dennis scan-qr --image --from-file file

Versioning Policy

  • DFP v1 payloads remain valid forever
  • No breaking changes allowed
  • Future versions must not reinterpret v1

Test Vectors

Security Considerations

DFP provides identity, not authenticity. Combine with signatures where required.

Summary

DFP v1 establishes deterministic identity, transport independence, explicit decoding semantics, and immutable version guarantees.
