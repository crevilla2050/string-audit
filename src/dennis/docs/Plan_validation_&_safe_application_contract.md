# Dennis Forge — Plan Validation and Safe Application Contract

**Contract ID:** DFC-PLAN-002  
**Version:** 2.0  
**Status:** Draft for review and adoption  
**Target release:** Dennis Forge 0.9.3  
**Project phase:** Pre-1.0.0 Beta  
**Supersedes:** Plan Validation and Safe Application Contract v1.x  
**Scope:** Canonical plan format, validation, apply eligibility, preflight, artifact inspection, execution safety, recovery, and regression protection.

---

## 1. Purpose

This contract establishes the canonical, testable safety boundary for transformation plans and their application in Dennis Forge.

Its purpose is to ensure that a plan cannot modify the filesystem unless its structure, integrity, completeness, operations, dependencies, targets, source assumptions, and execution authorization have been established before the first mutation.

The contract consolidates the decisions made during the Phase A audit of Dennis Forge 0.9.3.

It is an evolution of the previous contract, not a redesign of Dennis.

### 1.1 Governing principles

The implementation MUST respect the following principles:

1. **German Rule:** Wenn es nicht kaputt ist, repariere es nicht. Existing working behavior must not be rewritten without demonstrated need.
2. **Determinism:** Equivalent inputs under equivalent conditions must produce equivalent canonical plans and validation results. Unspecified ordering, timestamps, filesystem enumeration, or random collision resolution must not introduce hidden nondeterminism.
3. **Fail closed:** An invalid, incomplete, stale, or unsafe plan MUST NOT be applied.
4. **Preflight before mutation:** All predictable validation failures MUST be detected before the first filesystem mutation.
5. **Preservation:** Existing user files, artifacts, staging data, logs, and unrelated working changes MUST NOT be overwritten or deleted as incidental cleanup.
6. **Explicit authorization:** Validation and execution authorization are separate decisions.
7. **Reviewability:** Changes must be narrowly scoped, tested, and reviewable before proceeding to the next implementation step.
8. **CLI-first:** The safety contract belongs in the core application logic, not exclusively in the command-line interface.
9. **No unsupported atomicity claims:** Successful preflight does not guarantee that a multi-file operation can be rolled back atomically.

## 2. Version and compatibility policy

Dennis is pre-1.0.0 software. The project may establish a clean canonical contract now instead of preserving accidental inconsistencies between earlier implementations.

### 2.1 Canonical format

There MUST be one documented canonical plan format.

Newly generated plans MUST conform to the canonical schema. The generator, validator, artifact packer, and apply path MUST agree on that format.

The canonical schema is the authoritative definition of structural validity.

### 2.2 Legacy plans

Legacy compatibility is not mandatory.

A plan or artifact that does not satisfy the canonical contract MUST be rejected with a meaningful diagnostic. It MUST NOT be silently rewritten, partially interpreted, or accepted merely because it was previously generated by Dennis.

A migration mechanism may be introduced separately, with explicit input, output, and preservation guarantees. Automatic migration is outside this contract.

### 2.3 Existing user work

The compatibility policy does not authorize destructive repository operations.

Implementation MUST NOT reset, clean, stash, overwrite, stage, commit, or delete existing user work as part of Phase A. Such actions are outside the scope of this contract unless separately and explicitly authorized.

## 3. Canonical plan contract

The exact JSON Schema is an implementation deliverable governed by this section. The following requirements define the semantics that the schema and runtime validator MUST enforce.

### 3.1 Top-level structure

A canonical plan MUST contain:

- `meta`: canonical plan metadata.
- `changes`: the ordered set of planned operations.

The schema MUST reject malformed structures, invalid field types, unsupported operation values, and missing mandatory fields.

Unknown fields MUST be handled according to an explicit schema policy rather than silently acquiring operational meaning.

### 3.2 Metadata

The canonical metadata MUST contain:

| Field | Requirement |
|---|---|
| `meta.tool` | Nonempty identifier of the producing tool; canonical value is `dennis`. |
| `meta.version` | Nonempty version identifying the plan contract or producer version according to the finalized schema definition. |
| `meta.generated_at` | Valid timestamp representing plan generation time. |
| `meta.project_root` | Explicit project-root reference used to establish the plan's intended target scope. |
| `meta.dictionary` | The dictionary or transformation context required by the generator and applicable operations. |

Additional metadata may be defined only when its purpose and validation rules are documented.

The generator MUST emit metadata consistent with the schema. The schema MUST NOT require fields that the generator fails to produce.

`project_root` MUST have one documented interpretation. The apply implementation MUST NOT silently substitute the current working directory when the intended root is missing, invalid, or unavailable.

A missing or unusable project root is a validation failure.

Absolute versus relative root representation, relocation behavior, and timestamp normalization MUST be finalized explicitly in the schema implementation. They MUST NOT be left to inconsistent interpretations across modules.

### 3.3 Operation model

Every operation MUST have a recognized type and the fields required for that operation.

The currently observed operation families are:

- `replace`: replacement of existing source content.
- `helper`: helper-related operations, including the explicitly defined helper lifecycle behavior.

The implementation MUST inventory the existing helper modes and settle their canonical vocabulary before enforcing the schema. A mode MUST NOT be inferred from a missing field when doing so could change whether an operation creates or deletes files.

For replacement operations, the contract requires:

- A valid relative target file path.
- A valid source line reference.
- The expected original content.
- The replacement content.

For helper operations, the contract requires:

- A valid relative target path when a target file is involved.
- An explicit, supported helper operation mode.
- A valid helper identifier or reference, as appropriate.
- Any required helper source or dependency.
- All metadata necessary to validate the operation before execution.

The schema MUST express these requirements as precisely as the operation model permits.

Operations with missing fields, conflicting instructions, unknown types, or unsupported modes MUST be rejected.

### 3.4 Operation ordering

Operation order MUST have documented semantics.

The implementation MUST NOT depend on incidental dictionary order, filesystem enumeration order, or unstable collection ordering where that order affects results.

If operations are reordered or grouped internally, the transformation result MUST remain equivalent to the canonical operation semantics. Where ordering is significant, the plan MUST preserve and validate that ordering.

Duplicate-operation detection MUST use a documented definition of operation identity. Two legitimate operations MUST NOT be rejected merely because they share a file or line, while conflicting duplicates MUST NOT be silently applied.

## 4. Plan validation and eligibility

Validation MUST be implemented as a real, observable operation with a defined result. Loading a schema without validating the plan is not validation.

The core validator MUST return a structured result or raise a documented validation exception that callers handle consistently. It MUST NOT silently succeed, return an ambiguous value, or discard meaningful errors.

### 4.1 Independent eligibility conditions

A plan is eligible for application only when all applicable conditions pass:

1. **Structural validity:** The plan conforms to the canonical schema.
2. **Integrity:** Relevant hashes and artifact-integrity checks succeed.
3. **Completeness:** The plan represents a completed, eligible scan and contains all required information.
4. **Semantic validity:** Every operation and dependency is supported and internally consistent.
5. **Target safety:** All paths resolve within their permitted roots.
6. **Source validity:** Expected source content and required files match the plan's assumptions.
7. **Preflight success:** All planned operations and side effects have been checked.
8. **Authorization:** The requested execution and destructive operations have the required authorization.
9. **Confirmation:** Where the existing confirmation mechanism is required, the supplied confirmation matches the exact plan being considered.

No single condition substitutes for the others.

A matching confirmation hash MUST NOT make an invalid plan eligible. A valid plan MUST NOT be interpreted as automatic authorization to execute it.

### 4.2 Incomplete scans

A scan-only result containing findings is not automatically an executable transformation plan.

The implementation MUST distinguish scan results from complete plans. If a plan depends on a scan that did not complete successfully, the plan MUST be ineligible for application.

The canonical representation of scan completeness must be established explicitly. It MUST NOT be inferred merely from the existence of a `changes` array.

### 4.3 Validation diagnostics

Validation failures MUST identify the relevant field, operation, path, dependency, or eligibility condition whenever that information is available.

Diagnostics SHOULD be stable and actionable.

A malformed plan, an unsupported plan version, a missing source file, a stale replacement, and an unsafe archive MUST be distinguishable failure conditions.

## 5. Target-path and source validation

All target paths MUST be validated before mutation.

### 5.1 Root containment

Each target MUST resolve within its explicitly permitted root.

The implementation MUST reject:

- Absolute target paths where relative paths are required.
- Parent-directory traversal, including `..` escapes.
- Paths that resolve outside the permitted root.
- Symlink-based escapes.
- Invalid or ambiguous target paths.
- Targets that violate operation-specific filesystem requirements.

Containment checks MUST account for resolved filesystem paths, not merely string prefixes.

The implementation MUST define how missing targets are handled without relying on unsafe or inconsistent resolution behavior.

### 5.2 Source-root consistency

The plan's intended project root MUST be established before target resolution.

The current working directory MUST NOT silently determine the target of an otherwise ambiguous plan.

If the intended root cannot be established or verified, preflight MUST fail.

Any intentional support for relocating a project MUST use an explicit, documented rule. Relocation MUST NOT be an accidental consequence of running the command from another directory.

### 5.3 Source-content validation

For every replacement, preflight MUST verify that the expected original content can be matched according to the defined transformation semantics.

A missing or mismatched source line MUST be reported as a stale or invalid operation.

The apply path MUST NOT silently skip an unmatched replacement and report the plan as successfully applied.

The implementation MUST define behavior for ambiguous matches, repeated identical lines, line-number changes, whitespace normalization, and overlapping transformations. Those rules must agree with the generator and canonical plan semantics.

### 5.4 Helper dependencies

Every required helper file, identifier, reference, and lifecycle dependency MUST be resolved and validated before execution.

Helper removal MUST verify that the intended helper exists and that the requested removal corresponds to the plan's explicit operation.

A missing required helper, invalid helper reference, ambiguous helper target, or conflicting helper operation MUST cause preflight failure.

## 6. Complete apply preflight

Preflight is a mandatory phase between plan loading and execution.

The apply path MUST NOT begin mutating files while it is still discovering whether later operations are valid.

### 6.1 Required preflight checks

Before the first mutation, preflight MUST validate:

- Plan structure and canonical schema.
- Plan and artifact integrity.
- Scan completeness and apply eligibility.
- Confirmation and authorization requirements.
- Every operation type and its required fields.
- Every target path and root-containment condition.
- Every required source file.
- Expected original content and stale-operation conditions.
- Helper dependencies and lifecycle operations.
- Artifact-policy consequences.
- Log destination and log-writing prerequisites.
- Any additional filesystem preconditions required by the selected operations.

The preflight implementation MUST produce an execution-ready representation of the validated operations, or an equivalent immutable snapshot of the decisions it has made.

The execution phase MUST consume that validated representation rather than silently reinterpret the original plan.

### 6.2 All-or-nothing preflight

If any planned operation fails preflight, the entire plan MUST be rejected before any planned mutation occurs.

For example, if the first nine replacements are valid but the tenth has a missing source file, none of the ten operations may be applied.

This requirement concerns preflight rejection. It does not imply that a failure during execution can always be rolled back atomically.

### 6.3 Time-of-check/time-of-use changes

The implementation MUST recognize that files and paths can change between preflight and execution.

Before modifying a target, the execution layer SHOULD verify that relevant assumptions remain valid, including the expected source content and applicable path conditions.

If those assumptions have changed, execution MUST stop rather than apply a transformation against an unvalidated state.

The contract does not require a filesystem-wide transaction. Any stronger concurrency or atomicity guarantees must be specified and tested separately.

## 7. Safe DEX archive inspection

Artifact validation MUST NOT extract an untrusted archive before validating its members.

### 7.1 Archive-member validation

Before extraction, or before any equivalent filesystem write, the implementation MUST inspect the archive entries and reject unsafe members.

Validation MUST cover:

- Absolute paths and parent-directory traversal.
- Paths escaping the intended extraction root.
- Symlinks, hard links, and other special entries unless explicitly supported and safely handled.
- Duplicate or conflicting member paths.
- Unexpected file types.
- Invalid or conflicting required artifact entries.
- Malformed or corrupted archives.

The archive validator MUST not trust a filename merely because it appears under `payload/`.

### 7.2 Validation without extraction

Where practical, the validator SHOULD read the required plan and metadata directly from archive streams after validating the archive's member structure.

If extraction is required, it MUST occur only after member validation and MUST use a controlled destination with containment checks.

The original artifact MUST remain untouched during validation.

### 7.3 Plan and artifact consistency

The extracted or streamed plan MUST conform to the canonical plan contract.

Required artifact components MUST be present and consistent with the declared artifact structure. Integrity failures, missing plans, malformed JSON, and invalid plans MUST produce distinct, actionable diagnostics.

A malformed artifact MUST never reach the mutation phase.

## 8. Destructive operations and artifact policies

Destructive operations require explicit, operation-specific safety rules.

### 8.1 Helper removal

Helper removal MUST be represented by a recognized operation with explicit semantics.

Preflight MUST establish which helper is being removed, why it is in scope, and which file will be affected.

The implementation MUST NOT delete a helper based solely on a basename extracted from an unvalidated reference.

### 8.2 Artifact policies

The currently observed artifact policies are:

- `keep`
- `clean`
- `isolate`

Their canonical semantics MUST be documented and validated before execution.

`keep` MUST preserve the existing artifacts.

`clean` MUST NOT perform an unrestricted cleanup. It may remove only artifacts explicitly identified as eligible for removal under the validated policy.

`isolate` MUST NOT overwrite an existing destination or destroy an existing artifact as an incidental consequence of a naming collision.

If artifact isolation requires creating a bundle before removing source artifacts, source artifacts MUST remain intact until bundle creation and the required integrity checks have succeeded.

### 8.3 Explicit destructive authorization

Operations that remove files, delete directories, or otherwise destroy recoverable data MUST be covered by the authorization policy.

The authorization mechanism MUST identify the intended operation or scope. A general statement that a plan is valid is insufficient.

Preflight MUST reject a destructive operation when its required authorization is absent.

## 9. Determinism and collision handling

Determinism is a correctness requirement, not merely a packaging preference.

### 9.1 Deterministic behavior

Given equivalent canonical plans, equivalent source states, equivalent relevant dependencies, and equivalent authorization inputs, the validation and transformation decisions MUST be equivalent.

Timestamps may legitimately describe when a plan was generated. They MUST NOT silently determine target selection, transformation semantics, or collision resolution.

### 9.2 Artifact naming

Artifact isolation MUST NOT depend on the current time as an implicit collision-resolution strategy.

When the preferred destination already exists, the implementation MUST use a documented deterministic collision policy or fail safely.

It MUST NOT overwrite an existing destination.

A deterministic alternative may use a content-derived name, a canonical suffix, or another explicitly defined strategy, provided that it handles repeated collisions safely and preserves existing data.

### 9.3 Stable diagnostics and logs

Where practical, equivalent validation failures SHOULD produce equivalent structured diagnostics.

Filesystem enumeration and unordered collections MUST be normalized where their order affects externally visible output or execution decisions.

## 10. Logging, evidence, and recovery

The implementation MUST preserve evidence of validation and execution outcomes without introducing avoidable data loss.

### 10.1 Logging preflight

Before the first mutation, the implementation MUST validate the log destination and any required prerequisites for writing the execution log.

An invalid, inaccessible, or unsafe log destination MUST be detected before mutations begin when the log is a required part of the operation.

The implementation MUST define whether a log is mandatory for all application modes and how logging failures are handled.

### 10.2 Failure evidence

If execution fails after mutation begins, Dennis MUST report:

- The failure and its cause, where known.
- The operations completed before failure.
- The operation that failed.
- The resulting execution state, to the extent it can be established.
- The location of any retained recovery evidence or execution log.

Evidence MUST NOT be removed merely because execution did not complete successfully.

### 10.3 Preservation of staging and existing data

Validation and recovery MUST NOT perform blanket cleanup of staging directories.

Pre-existing files, artifacts, logs, and recovery evidence MUST NOT be overwritten or deleted without establishing that the specific target is safe to replace or remove and that the action is authorized.

Temporary directories created by the current operation may be cleaned up only when doing so cannot destroy pre-existing data or evidence needed for recovery.

### 10.4 Recovery guarantees

Phase A guarantees rejection of known invalid plans before mutation and preservation of relevant evidence on failure.

It does not promise automatic rollback of every partially executed operation.

If rollback or transactional application is introduced later, it MUST have its own explicit contract, failure model, and regression tests.

## 11. Implementation architecture

The implementation MUST establish clear responsibilities between components.

### 11.1 Plan generator

The generator MUST emit the canonical plan structure, metadata, operation fields, and completeness information required by the schema.

It MUST NOT emit a plan that its own validator rejects under the same contract.

### 11.2 Schema validator

The schema validator MUST enforce the canonical structural contract and return meaningful validation results.

It MUST be used by the relevant application paths rather than remaining an isolated or unfinished helper.

### 11.3 Artifact validator

The artifact validator MUST validate archive structure safely, obtain the canonical plan without unsafe extraction, and enforce plan-level integrity and validity.

### 11.4 Apply preflight

The preflight layer MUST resolve and validate the complete execution scope before mutation.

It MUST keep validation, authorization, confirmation, and execution distinct.

### 11.5 Apply executor

The executor MUST consume the preflight-approved operations and enforce the agreed execution assumptions.

It MUST report partial execution accurately and retain relevant evidence if a runtime failure occurs.

### 11.6 Compatibility with the existing architecture

These responsibilities MUST be implemented using the existing Dennis architecture wherever practical.

Phase A is not authorization to replace the apply system wholesale, introduce a parallel transformation engine, or redesign the plugin API.

The smallest coherent implementation that satisfies this contract is preferred.

## 12. Acceptance tests

Phase A is not complete until the following test categories pass.

### 12.1 Canonical schema and generator

- A valid generated plan passes schema validation.
- Missing mandatory metadata is rejected.
- Invalid field types and malformed structures are rejected.
- Unsupported operation types and modes are rejected.
- Generated metadata and the declared schema agree.
- Supported plan generation behavior remains intact.
- Incomplete scan results cannot be applied.
- Legacy plans that violate the canonical contract receive explicit validation errors.

### 12.2 Apply eligibility

- A structurally invalid plan cannot be applied with a matching confirmation hash.
- An integrity failure prevents application.
- An incomplete plan prevents application.
- Missing authorization prevents destructive execution.
- Missing required confirmation prevents execution where confirmation is required.
- A valid plan remains subject to the other eligibility checks.

### 12.3 Complete preflight

- Every operation is checked before mutation.
- A missing target or dependency prevents all planned mutations.
- A stale replacement prevents all planned mutations.
- An ambiguous or conflicting operation is rejected.
- An invalid log destination is rejected before mutation when logging is mandatory.
- A target outside the permitted root is rejected.
- Symlink-based path escapes are rejected.
- A change to relevant source assumptions before execution is detected where the implementation can safely verify it.

Each failure test MUST verify filesystem state, not merely an error message.

### 12.4 Archive safety

- A valid canonical artifact passes validation.
- A malformed or corrupted archive is rejected.
- Missing `payload/plan.json` is reported.
- Malformed plan JSON is reported clearly.
- Absolute paths and parent-directory traversal are rejected.
- Unsafe links and special entries are rejected unless explicitly supported.
- Duplicate or conflicting member paths are rejected.
- No malicious archive can write outside the intended extraction root.
- The original artifact remains unchanged during validation.

### 12.5 Helper lifecycle and transformations

- Valid helper operations continue to work.
- Missing helper dependencies prevent application.
- Invalid helper references are rejected.
- Explicit helper removal affects only the authorized target.
- Valid replacement operations retain their intended transformation behavior.
- Missing or stale source content is not silently skipped.
- Overlapping and repeated-line behavior follows the canonical transformation rules.

### 12.6 Artifact policy and evidence preservation

- `keep` preserves artifacts.
- `clean` removes only eligible artifacts within the validated scope.
- `isolate` preserves the source until successful bundle creation and verification.
- Existing isolation destinations are never overwritten.
- Collision handling is deterministic or fails safely.
- Failure before mutation leaves the filesystem unchanged.
- Failure after mutation begins produces accurate diagnostics and retains relevant evidence.
- Pre-existing staging content and unrelated user work remain intact.

### 12.7 Regression protection

Regression tests MUST cover the existing supported preview, confirmation, helper operations, ordinary transformations, and artifact-policy behavior.

Tests MUST also cover the relevant CLI integration paths, including plan validation and artifact validation.

A passing unit test for the validator alone is insufficient to establish that the application path enforces the contract.

## 13. Implementation sequence

Implementation MUST proceed through bounded, reviewable checkpoints.

**Checkpoint A — Canonical contract and schema**

1. Finalize canonical metadata, operation types, helper modes, and root semantics.
2. Update the schema to express those decisions.
3. Align plan generation with the schema.
4. Implement actual structural validation.
5. Add generator/schema regression tests.

**Checkpoint B — Apply eligibility and preflight**

1. Separate validation, completeness, confirmation, and authorization.
2. Establish a complete preflight representation.
3. Validate every operation, dependency, source file, and target.
4. Prevent mutation if any preflight check fails.
5. Add filesystem-state assertions to failure tests.

**Checkpoint C — Safe artifact validation**

1. Inspect archive members before extraction or equivalent writes.
2. Reject unsafe members and conflicting paths.
3. Validate the canonical plan and artifact contents.
4. Test malicious and malformed archives.

**Checkpoint D — Destructive operations and evidence**

1. Formalize helper-removal and artifact-policy semantics.
2. Protect existing staging and isolation destinations.
3. Remove time-dependent collision naming.
4. Validate logging prerequisites.
5. Test failure paths and evidence preservation.

**Checkpoint E — Integration and release gate**

1. Run the relevant unit and integration suites.
2. Review the complete diff.
3. Confirm that existing user work has not been disturbed.
4. Record unresolved limitations explicitly.
5. Verify the 0.9.3 release candidate against this contract.

Each checkpoint MUST pass its acceptance tests and receive review before proceeding to the next.

## 14. Scope exclusions

The following are outside this contract unless separately approved:

- A wholesale rewrite of `apply_plan()`.
- A redesign of the plugin API.
- Automatic migration of legacy plans.
- A new transaction or rollback subsystem.
- A redesign of the confirmation mechanism beyond the safety requirements defined here.
- BDEX implementation.
- Unrelated database, ORM, UI, or repository cleanup.
- Changes to unrelated DEX lineage or provenance semantics.

These exclusions do not prevent a narrowly scoped change when implementation evidence demonstrates that it is necessary to satisfy a requirement of this contract.

## 15. Completion criteria

Phase A is complete only when:

1. The canonical plan contract is unambiguous and implemented.
2. The generator emits plans accepted by the canonical validator.
3. Every apply path enforces eligibility and complete preflight.
4. Unsafe archive members are rejected before filesystem writes.
5. Destructive operations are validated and explicitly authorized.
6. Deterministic collision behavior and evidence preservation are implemented.
7. Required regression tests pass.
8. The implementation diff has been reviewed.
9. No known Phase A acceptance failure remains unresolved.
10. The release decision records any limitations that remain outside the contract.

A passing test suite is necessary but not sufficient if known unsafe behavior remains untested or unaddressed.

## 16. Final governing rule

**No plan may mutate the filesystem until Dennis has established that the plan is structurally valid, complete, intact, semantically applicable, safely scoped, preflight-approved, and authorized for the requested operations.**

When a condition cannot be established, Dennis MUST fail safely, explain the reason, and preserve existing work and relevant evidence.

This contract establishes the required behavior. The implementation must demonstrate that behavior through code inspection and tests rather than treating the contract itself as proof of safety.
